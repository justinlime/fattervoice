# AGENTS.md

## Project Name

This project is named `fatterqwen`.

## Repository Context

This repository contains another repository, `faster-qwen3-tts`, which is the basis for this project.

`faster-qwen3-tts` is the upstream/reference implementation we are building on top of. Its README and examples should be treated as the initial technical reference for model behavior, supported generation modes, streaming behavior, and performance characteristics.

When working in this repo:

- Treat `faster-qwen3-tts` as the core inference engine.
- Prefer wrapping and integrating it rather than re-implementing its model internals.
- Use the upstream README as the first source of truth for model options and expected behavior.
- Preserve or improve its speed and voice cloning quality whenever possible.

## Project Goal

The goal of `fatterqwen` is to build a Python wrapper around `faster-qwen3-tts` using `uv` instead of `pip`.

This wrapper will expose the model as a production-oriented Text To Speech server.

The server must support:

- OpenAI API compatible TTS endpoints
- streaming responses for OpenAI-compatible endpoints
- Wyoming protocol support for Home Assistant
- streaming support for Wyoming protocol where practical and supported by the client/protocol flow

The server accepts text input through those interfaces and emits TTS audio generated by the model provided by `faster-qwen3-tts`.

## Primary Priorities

The top priorities of this project are:

1. accurate voice cloning
2. fast inference / low latency
3. low VRAM usage
4. stable VRAM usage over time

“Stable VRAM usage” means runtime memory usage should remain as predictable as possible and should not spike significantly between requests unless strictly required.

When making implementation decisions, optimize for:

- best achievable voice similarity to the reference speaker
- high streaming responsiveness
- high real-time factor / throughput
- minimal memory churn
- predictable long-running server behavior

## Voice System Contract

The server will have a `voices/` directory.

Each voice is defined by:

- a valid reference audio file
- a matching transcript `.txt` file

The transcript is required because the model is believed to produce more accurate cloning when it is given the transcript of the reference audio.

Every voice must have a transcript.

### Voice Pairing Rules

A transcript belongs to a reference audio file by matching basename.

Examples:

- `voices/hank.wav` -> transcript must be `voices/hank.txt`
- `voices/jane.flac` -> transcript must be `voices/jane.txt`

Rules:

- the basename is the identifier
- the audio extension may vary if supported by the implementation
- the transcript extension is always `.txt`
- the filename basename becomes the external `voice` identifier exposed through the API/protocol interfaces

So a request selecting voice `hank` should resolve to:

- reference audio: `voices/hank.wav` or other supported audio file with basename `hank`
- transcript: `voices/hank.txt`

### Voice Selection Semantics

The basename of each voice file is the canonical voice ID used by clients.

This voice ID must be accepted by:

- OpenAI-compatible TTS endpoints
- Wyoming/Home Assistant integration

If multiple audio files share the same basename with different extensions, that should be treated as a configuration error unless the implementation explicitly defines a precedence rule.

## API and Protocol Requirements

### OpenAI-Compatible API

The server must expose OpenAI API compatible TTS endpoints, including streaming support.

At minimum, the implementation should target compatibility with the OpenAI-style speech generation contract used by common clients and tools.

The voice selection field should map directly to the basename-derived voice ID from the `voices/` directory.

### Wyoming Protocol

The server must also expose Wyoming protocol support for Home Assistant.

The implementation should make voice selection available through Wyoming in a way that maps cleanly onto the same internal voice registry used by the OpenAI-compatible endpoints.

### Shared Internal Design Requirement

Avoid building two completely separate synthesis stacks.

Prefer one shared internal synthesis service that:

- resolves the selected voice
- loads reference audio and transcript
- applies model/runtime options
- invokes `faster-qwen3-tts`
- returns either full audio or streaming chunks

The OpenAI-compatible layer and Wyoming layer should be thin adapters over the same internal engine.

## Configuration Rules

This project is Docker-first.

All runtime configuration must be available through command-line flags, with environment variable fallbacks.

CLI flags are the primary configuration interface.
Environment variables are the fallback.

At minimum, users must be able to configure:

- voices directory
- listen address
- port
- model type (`0.6B` or `1.7B`)

If there are model-specific tuning parameters or runtime options, they must also be exposed through CLI flags and mirrored by environment variable fallbacks.

Examples of likely configurable runtime options include, if supported by the final implementation:

- chunk size
- device selection
- dtype / precision mode
- non-streaming-mode behavior if relevant to quality/performance
- append-silence behavior for reference audio handling
- concurrency limits
- model cache path
- preload / warmup behavior
- request timeout or max text length
- Wyoming-specific bind/config options

### Configuration Philosophy

- CLI first
- ENV fallback
- explicit defaults
- documented behavior
- no hidden internet-dependent runtime setup

## Dependency and Packaging Requirements

This project should use `uv` rather than `pip` for project workflows.

When adding developer or runtime setup instructions:

- prefer `uv`
- prefer `pyproject.toml`-based project management
- keep the developer workflow simple and reproducible
- avoid unnecessary packaging complexity

## Docker and Offline Requirements

This project has a strict requirement that the Docker image must be fully usable without internet access after it has been built.

That means:

- all Python dependencies must be available in the image
- all runtime dependencies must be available in the image
- all required model artifacts must be cached in the image
- the container must not need to fetch models, packages, or assets on startup
- the container must remain functional in a fully offline environment after build completion

### Docker Expectations

The container should be designed for CUDA runtime support.

The image/build process should:

- pre-fetch required model files during build
- cache dependencies during build
- avoid startup-time downloads
- make offline execution the default expectation, not an optional mode

If multiple model variants are supported, the image/build strategy should clearly define whether:

- one image contains both models, or
- separate images/tags are produced per model

That tradeoff should be evaluated against image size, startup speed, and offline usability.

## Model Support

The initial project scope must support at least:

- `0.6B`
- `1.7B`

Model selection must be configurable via CLI flag and ENV fallback.

The implementation should preserve the ability to expose relevant upstream tuning/runtime options when they materially affect:

- speed
- latency
- voice quality
- VRAM usage
- VRAM stability

## Performance and Quality Guidance

Future contributors and coding agents should treat the following as strong guidance:

### Voice Cloning Quality

- accurate voice cloning is more important than broad feature expansion
- always prefer using the matching transcript for each reference audio
- do not make transcript optional in the normal voice-directory flow
- preserve upstream behaviors that improve cloning quality unless there is a strong reason to change them

### Streaming

- streaming support is a first-class feature, not an afterthought
- avoid designs that force full-audio buffering when chunked output is possible
- measure time-to-first-audio and sustained throughput when evaluating changes

### VRAM

- prefer predictable memory behavior
- avoid repeated model reloads
- avoid request handling patterns that cause large memory spikes
- reuse model state and caches where safe
- be cautious with concurrency if it harms latency or memory stability

### Runtime Tradeoffs

When a tradeoff exists between features and the top priorities, prefer:

1. voice cloning fidelity
2. speed
3. VRAM stability
4. secondary convenience features

## Implementation Guidance

When extending this project, prefer an architecture like:

- `config` layer for CLI/ENV resolution
- `voice registry` layer that scans `voices/` and validates audio/transcript pairs
- `model service` layer that wraps `faster-qwen3-tts`
- `OpenAI-compatible API` adapter
- `Wyoming` adapter
- `Docker/offline build` assets and model caching strategy

### Voice Registry Expectations

The voice registry should:

- scan the configured voices directory
- match supported audio files with `.txt` transcripts by basename
- reject incomplete pairs
- provide a canonical list of available voice IDs
- expose metadata needed by both API layers

### Validation Expectations

Startup validation should fail fast for:

- missing voices directory
- missing transcript for an audio file
- unsupported or unreadable audio files
- duplicate basename conflicts
- invalid model selection
- missing cached model assets in an offline-required deployment mode

## Upstream Reference

Use `faster-qwen3-tts` as the basis of the project.

Its README should be the initial reference for:

- supported model IDs
- streaming behavior
- OpenAI-compatible example behavior
- quality/performance tuning options
- CUDA-related expectations

Prefer adapting upstream examples and proven code paths before inventing new ones.

## Non-Goals for Early Work

Unless explicitly requested, do not prioritize:

- unrelated UI work
- cloud-only assumptions
- internet-required startup flows
- feature additions that significantly reduce cloning quality or speed
- configuration only available through environment variables without CLI support

## Summary

`fatterqwen` is a Docker-first, offline-capable, CUDA-targeted Python TTS server wrapper around `faster-qwen3-tts`, managed with `uv`, exposing OpenAI-compatible and Wyoming interfaces with streaming support, using basename-matched reference audio and transcript pairs from a `voices/` directory to maximize voice cloning quality while keeping inference fast and VRAM usage low and stable.
